# Fleng English — звіт про виправлення проходження уроку

Гілка `fix/lesson-test-flow`. Вихідна діагностика — [FLENG_TEST_FLOW_REPORT.md](FLENG_TEST_FLOW_REPORT.md), коміт `9c30e93`. Реалізація, тести й документація — коміт `2486790`. Цей звіт збережено окремим комітом.

## Що виправлено

1. **FIFO.** Сервер повертає `pendingExerciseIds` у відповідях start, progress і submit. Ще не виконані вправи без спроб ідуть у порядку уроку. Після кожної помилки вправа переходить у кінець за часом останньої збереженої спроби. Вправа має один запис на пару «учень і вправа», тому повторна помилка переміщує її без дублювання. Правильна відповідь вилучає вправу з черги. Усі формати користуються спільним переходом. Правила оцінювання, завершення та одноразового XP збережено.
2. **Відновлення.** Прогрес, завершені й невиконані вправи, порядок повторів та XP відновлюються із сервера. Поточна вправа зберігається в `sessionStorage` для пари «учень і урок» у межах вкладки. Курсор відновлюється, якщо ID вправ і лічильники спроб збігаються з серверним знімком. Інакше відкривається голова актуальної черги. Після завершення уроку запис курсора очищається.
3. **Самооцінка.** Учень вводить відповідь і натискає «Підтвердити відповідь і показати зразок». Захищений запит відкриває зразок без запису спроби, активності чи XP. Після цього учень бачить підтверджений текст, зразок та кнопки самооцінки. Вибір оцінки зберігає результат і запускає той самий перехід, що й решта форматів.

### Повторні запити та мережа

Кнопки й поля блокуються під час надсилання. Enter скасовує таймер перевірки. Браузер передає `expectedAttempts`. Якщо поточне число спроб змінилося, сервер під наявним блокуванням учня повертає `409 LESSON_ATTEMPT_CHANGED` до запису нової спроби. Коли відповідь API втрачена, браузер перевіряє серверний прогрес перед повторним надсиланням. Якщо перезавантаження сталося під час POST, нова сторінка може кілька разів перечитати прогрес протягом короткого вікна. Ці GET-запити не повторюють відповідь учня.

## 12 сценаріїв до та після

Повторено в Chromium через Playwright на реальному FastAPI з тимчасовою файловою SQLite. Для мережевих сценаріїв Playwright керував доставкою запитів і відповідей. Оцінювання та запис виконував FastAPI.

## Інші перевірки

- **Chromium E2E** — 47 пройшли, включно із сімома новими. Набір запущено з окремим локальним сервером і тимчасовим конфігом Playwright, щоб уникнути зависання штатного завершення сервера на Windows. Перший прогін із попередньою версією тестів мав застарілий сценарій, що шукав кнопку надсилання для автовибору, і таймаут мережевої перевірки. Старий сценарій відтворився на `9c30e93`. Сценарій оновлено для справжньої події вибору, а фінальний набір завершився з кодом 0.
- **Backend pytest** — 2686 пройшли, 3 впали, 35 пропущено у повному прогоні. Новий API-тест зразка, доданий після початку збору повного набору, пройшов окремо. Сукупно перевірено всі 2725 зібраних тестів, з них 2687 пройшли. Три падіння відтворено на `9c30e93`: `test_transfer_reads_private_snapshot_before_connecting` використовує недопустимий у Windows символ `?` у назві файлу, `test_worktree_with_missing_database_is_refused_with_a_remedy` порівнює різні роздільники шляхів, `test_sqlite_requires_both_mounted_disk_and_path_beneath_it` використовує POSIX-шлях `/var/data`.
- **JavaScript** — 138 пройшли, 14 впали. Такий самий результат отримано з архіву коміту `9c30e93`. 13 тестів AI-віджета не можуть імпортувати `getCourse` з тестового модуля. Один тест Windows-лаунчера читає `source` зі значення `null`. Зосереджений набір `test-courses.mjs` пройшов 26/26. Обидві PWA-перевірки пройшли.
- **Інші команди** — Ruff, mypy, перевірка документації та OpenAPI, `pip check`, перевірка залежностей, валідатор курикулуму та `git diff --check` пройшли. Migration smoke підтвердив один Alembic head, повторний upgrade, відповідність ORM і цілісність тимчасової БД. Процес повернув помилку при прибиранні відкритого файлу SQLite на Windows `WinError 32`. Цю помилку також відтворено на `9c30e93`.

## Невирішене й потенційні ризики

- Серверний порядок і XP перевірено на SQLite. Live PostgreSQL не використовувався. Інші браузери не запускалися.
- Курсор відновлюється в тій самій вкладці. Нова вкладка, інший пристрій або недоступне сховище відкривають голову серверної черги.
- Якщо мережа довго недоступна або POST завершується після короткого вікна повторних GET, актуальний стан буде доступний через наступне завантаження чи відповідь API. Захист за номером спроби діє під час повторного надсилання з оновленого клієнта.
- Для старих записів з однаковим часом останньої спроби точний історичний порядок невідомий. Для них порядок стабілізується за ID. Нові спроби впорядковуються під серверним блокуванням навіть за збігу часу.
- Непідтверджений текст і відкритий зразок до остаточної самооцінки є станом сторінки. Після reload збережена спроба відновлюється із сервера, а незавершену самооцінку потрібно почати з підтвердження відповіді.
